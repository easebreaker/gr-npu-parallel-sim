## 一、先分清三种「混合」

这三个概念经常被混为一谈，但仿真结果完全不同。**本框架的结论依赖这个区分。**

| 形态 | 卡怎么用 | 单请求 | 多请求 |
|---|---|---|---|
| **A. 逐段换切分** | 全部卡，每段用自己合适的切分 | **最优**（段间串行，卡可复用） | 同左 |
| **B. 段级卡组划分** | 卡分成若干组，各组负责不同段 | **必然更差**（每段只有部分卡） | 无收益 |
| **C. 并发异构** | 卡分成若干组，各组服务不同请求 | — | 需满足两个条件才赢 |

用户直觉里的「混合更好」在 **A** 上成立；如果理解成 **B**，则不成立。
**这个区分是本框架最主要的输出。**

## 二、为什么 A 会赢：一条切分对不同算子作用完全不同

| 切分 | 查表 | 线性投影 | 自注意力 | 其它段 |
|---|---|---|---|---|
| `embp`（切表） | **有效**：访存 /N | 复制 | 复制 | 复制 |
| `cp_q`（切 Q） | 复制 | **有效**（token 维） | **有效**：算力 /N | 复制 |
| `tp` | 复制 | **有效** | 复制 | 复制 |

「复制」= 这 N 张卡各自把这一段完整做一遍，聚合工作量 ×N，**时间与单卡相同**。
于是：

- **纯 CP** 的浪费：查表段被复制 N 份，且表不切 → 每卡都持有全表（显存 ×N）。
- **纯 EmbP** 的浪费：注意力段被复制 N 份 → 每卡都算整段 L²。
- 两者浪费的是**不同的段**，所以逐段混搭能同时避开。

还有一条只属于 CP 的不对称：只切 Q 时 **KV 不切**，每卡都要读整段 KV，
所以聚合访存 ×(1+N)/2（N=8 时 4.5 倍）。这条让 CP 在没有 L² 的模型上净亏。

## 三、四个模型的结构差异（仿真的输入）

| 模型 | 注意力增长律 | 由什么决定 | 适合的方案 |
|---|---|---|---|
| MTGR / HSTU | **L²** | 整段自注意力，分数矩阵 B·h·L² | CP 收益最大 |
| LONGER | **L·T** | 组内注意力 R=⌊L/T⌋，每组长 T | CP 只拿线性收益 |
| HyFormer | **无**（decode 是 short×short） | 注意力段与用户序列无关 | CP 无用；靠并行的只有查表 |

注意 HyFormer 整网仍随 L 增长，但**不是因为注意力，而是因为查表每 token 一次**。
这一点由 `tests/test_hetero.py::test_growth_order_matches_structure` 单独断言：
它的 `seq_cross` / `decode` / `boost_*` 四段时间在 L 变化 16 倍时完全不变。

### cost.py 的核心：`helps()`

```python
def helps(split_kind, operator):
    if split_kind == "embp":  return operator == "lookup"
    if split_kind == "cp_q":  return operator in ("self_attn", "group_attn", "cross_attn", "linear")
    if split_kind == "tp":    return operator == "linear"
    return False
```

不吃这条切分的段 → `aggregate()` 返回 `×N` 的工作量。
**整个框架的定性结论都由这一条函数决定**，改它就会改结论。

### 两处物理修正

- **随机访存惩罚**（`gather_eff=0.15`）：查表是随机 gather，与流式搬运不能共用
  一个带宽。官方口径下访存合并前后差距可达数倍。
- **CP 的 KV 不切**：`cp_q` 对注意力段把聚合访存放大 `(1+N)/2`。

## 五、前八节演示的结论

1. **结构**：四个模型的阶段图与源码一致；增长律分别是 L² / L·T / 无。
2. **长度敏感性**：MTGR 29×（L 涨 16 倍），LONGER 14×，HyFormer 5×（来自查表）。
3. **纯 CP vs 纯 EmbP vs 混搭**：**混搭在三个模型上都最优**，但赢的理由不同。
   - MTGR：纯 EmbP 亏 7 倍（注意力被复制），纯 CP 亏约 7%（查表被复制 + 表不切）。
   - LONGER：注意力是 L·T，CP 收益本来就小，混搭省下的是复制开销。
   - HyFormer：纯 CP 比纯 EmbP 还差 —— 没有 L² 可切，CP 只带来 KV 放大。
4. **混搭方案细节**：MTGR L=8192 时，`embed` 走 EmbP（1.4%）、`proj` 与 `attn`
   走 CP（98.6%）。**混搭不是在切分上取巧妙，而是让不吃的段不要被强行套上切分。**
5. **段级卡组划分（B）**：比混搭慢 3.4 倍，**且每卡常驻反而更高**（表只切 4 份而非 8 份）。
   单请求上两个维度都更差 —— 它没有存在的理由。
6. **并发（C）**：一条 9.4 ms 的 MTGR + 一条 0.12 ms 的 HyFormer，分卡后 makespan 反而
   变长（长的请求主导，分卡让它慢一倍）。**并发只在两条请求时长可比、且瓶颈不同时才赢。**
7. **失效条件**：两条都算力 bound → 吞吐比 1.01×（等于没有并发）；两条都 EmbP →
   链路争用；显存装不下 → 直接不可行。
8. **表大小的分水岭**：64 GB 卡上，50M 行（6 GB）两种都行；900M 行（107 GB）时
   纯 CP 完全不可行，**混搭从性能选择变成可行性条件**。

## 六、这套仿真不能回答什么

- **绝对时间不可信**。`cube_eff=0.25`、`gather_eff=0.15` 都是拍的；真实 η 要实测
  （本框架只给方向；实测方法见配套仓库的时间预测工作）。
- **没有建模链路拓扑细节**。HCCS 是 8 卡全互联，这里当成一条共享总线；
  若换机架式或跨机，`v` 应分两档（跨机与机内的每字节代价差约一个量级）。
- **没有建模请求到达过程**。并发那一节比的是两条固定请求的 makespan，
  不是排队论下的吞吐。
- **没有建模 kernel 级融合差异**。同一段在不同实现下可能是 1 个或 3 个 kernel，
  这里按 `n_kernel` 一个数给了。

## 七、如果要落到实测

最省的三步（对应上面三个最可能的反驳）：

| 步骤 | 验什么 | 成本 |
|---|---|---|
| 1 | 纯 CP 与纯 EmbP 的**同一段**时间比 | 每个模型 2 次，看 `helps()` 的方向对不对 |
| 2 | 纯 CP 部署是否真的把表复制到每卡（看显存） | 1 次，`msprof` 看 HBM 占用 |
| 3 | 混搭方案（A）的端到端时间是否优于两个纯方案 | 每模型 3 次 |

那要先改 `models.py` 的阶段图，而不是调参数。

## 八、共置配对：你说的那个场景

前面第一节区分了三种「混合」，但你的想法其实是**第四种**，我之前没建：

> 四个模型，a/b 走 EmbP、c/d 走 CP。卡分两组，a 与 b 挤在一组、c 与 d 挤在另一组。
> 你认为这样不如 a 配 c、b 配 d。

这是**共置配对**（co-location pairing）：多个请求**共享同一组卡**，
而不是像第三节的「分卡并发」那样各占一组。两者的区别是关键：

| | 分卡并发（§6） | 共置配对（§9） |
|---|---|---|
| 卡 | 各请求占**不相交**的卡组 | 多个请求**共享**同一组卡 |
| 争用 | 只有链路（全芯片共享） | 算力、访存、链路**全部**争用 |
| 收益来源 | 长的那个不再等短的 | 不同资源可以重叠推进 |

### 机制：资源池

一个请求在 N 卡上可以拆成三项需求（`job_demand`）：算力、访存、链路。
`colocate` 把它们**逐项相加**，再取最大分量作为 makespan：

```
makespan = max( Σ算力/N·P , Σ访存/N·BW , Σ链路/N·link )
```

于是：一个算力密集 + 一个访存密集 → 两项分别跑，重叠推进；
两个算力密集 → 算力项相加，只能串行。

### 真实四个模型的结果（每组 4 卡）

| 请求 | 算力 ms | 访存 ms | 链路 ms | bound |
|---|---|---|---|---|
| a-HF | 0.01 | 0.11 | 0.03 | **访存** |
| b-HF | 0.02 | 0.18 | 0.06 | **访存** |
| c-MT | 2.87 | 1.40 | 0.07 | **算力** |
| d-MT | 6.87 | 2.69 | 0.14 | **算力** |

资源向量余弦：`a+b` 0.999、`c+d` 0.997（同类）；`a+c` 0.544、`b+d` 0.465（互补）。

| 配对 | 组1 | 组2 | makespan |
|---|---|---|---|
| (a+b) ｜ (c+d) | 0.29 ms | 9.75 ms | **9.75 ms** |
| (a+c) ｜ (b+d) | 2.89 | 6.90 | **6.90 ms** |
| (a+d) ｜ (b+c) | 6.89 | 2.90 | **6.89 ms** |

**你的判断成立：同类配同类最差，差 1.42 倍。**

### 但收益有两个来源，必须分开

真实模型上，异类配对变快是两件事叠加：

1. **负载均衡**：`c+d` 那组把两个长序列塞进 4 卡，成了瓶颈（9.75 ms），
   而 `a+b` 那组 0.29 ms 就结束、空转。把便宜的 HF 挪过去就摊平了。
2. **资源互补**：算力与访存真的能重叠。

用归一化画像（span 都设为 1，只改占比）做对照，可以单独看第二项：

| 配对 | 同质 | 异质 | 加速 |
|---|---|---|---|
| 纯算力 vs 纯访存 | 2.00 span | 1.00 span | **2.00×** |
| 9:1 vs 1:9 | 2.00 | 1.11 | **1.80×** |
| 6:4 vs 4:6 | 2.00 | 1.67 | **1.20×** |

结论有三条：

- **同质配对的 makespan 恒为 2.00 span**，与两个请求多便宜无关——同类只能串行。
- **异质配对的收益 = 2 / max(重合资源之和)**，完全互补时 2×，6:4 混合时只有 1.20×。
- **收益上界由资源画像的重叠度决定**，不取决于谁贵谁便宜。

### 什么时候换配对根本没用

若两条请求画像完全相同（例如都是长序列 MTGR，85% 算力），
三种配对方式的 makespan **完全一样**。这时唯一出路是时间维度的错峰，
不是空间维度的重排：让两条请求共享卡组、调度器愿意交错，
一条在算力段时另一条正好在查表段。**这不需要静态配对，只需要不做静态绑核。**

### 仿真模型的两处乐观

- `colocate` 假设**完美交织**：三项需求各自相加后取最大，等于假设资源可以被
  无损耗地分时复用。这是收益的**上界**，不是可实现值。
- 没有建模请求的到达过程。这里比的是「四个请求、一小段时间内的 makespan」，
  不是排队论下的稳态吞吐。

### 怎么验证

三次请求就能判断方向：

1. 单独跑 `a-HF` 与 `c-MT`，量它们的算力/访存占比 → 验证 `bound` 标签
2. 同卡共置 `a-HF + a'-HF`（两个同类），量 makespan
3. 同卡共置 `a-HF + c-MT`（一访存一算力），量 makespan

若第 3 步没有比第 2 步的一半更快，说明真实硬件上的资源无法重叠
（例如调度器不做交错，或 HBM 带宽已被某一方吃满），
那这个方向的收益就不存在。

## 九、副卡提前释放与段级交错

详细论证见 `段级交错-与LLM的差异.md`（含文献来源与建模更正）。

### 9.1 空隙不来自切分，来自 kernel 的最短时长

每段都用满 8 卡时，利用率 99.8%，**没有任何空隙**。真正让卡空转的是
**单次 kernel 有最短时长**（仿真取 60 μs）：工作量低于它之后，加卡不再更快。

| L=256 | cp1 | cp2 | cp4 | cp8 | 够用卡数 |
|---|---|---|---|---|---|
| embed | 0.090 | 0.090 | 0.090 | 0.090 | **1** |
| proj | 1.277 | 0.699 | 0.409 | 0.360 | 8 |
| attn | 0.360 | 0.368 | 0.366 | 0.363 | **1** |

L=256 时 `attn` 在 1 卡与 8 卡上同速，那 7 张卡是纯空转。
L=2048 时 `attn` 必须用满 8 卡（2.364 → 0.428）。

**判据是「该段是否触及 kernel 下限」，不是「切分度多高」。**

### 9.2 段级交错：收益集中在短请求

| L | 请求级 | 段级交错 | 加速 |
|---|---|---|---|
| **256** | 6.672 ms | **3.984** | **1.67×** |
| **512** | 7.066 | 4.378 | **1.61×** |
| 2048 | 14.550 | 14.382 | 1.01× |
| 16384 | 223.356 | 223.188 | 1.00× |

### 9.3 混合负载上被稀释

32 个随机长度的请求：请求级 82.6 ms → 分桶后逐桶交错 **79.3 ms，只有 1.04×**。
因为 L=8192 那一桶独占 28.8 ms，短桶省下的几毫秒只占零头。

**定位必须收窄**：适合短请求为主的批处理（预热、离线回填、尾批），
不适合通用混合在线负载。

### 9.4 分桶是「能不能批」的前提

不同 L 的最优卡数不同，同批要求卡数一致，所以混合长度**不能同批**
（`ValueError: 段 attn 在不同请求上卡数不同`）。

### 9.5 两个调度器

| 函数 | 语义 | 对应真实系统 |
|---|---|---|
| `greedy_schedule` | 按到达顺序，请求整体跑 | vLLM / Orca 的请求级批处理 |
| `backfill_schedule` | 最早可行时刻回填 | Sarathi 式迭代级调度的简化 |
| `stage_batched_schedule` | 逐段批处理，允许不同请求在不同阶段 | RecPipe 的 sub-batch 流水（但粒度不同） |

`card_time_floor` 给出不可达到的下界（总卡时 / 卡数，且不小于最长请求的
关键路径），用来衡量一个调度还剩多少空间。

## 十、只有部分段可并行时的冗余（卡级 Amdahl）

详细论证见 `冗余段处理-文献与GR方案.md`。

### 10.1 「冗余」有两种解释

| 情形 | 其他 N−1 卡在做什么 | A/C/D 重复是 |
|---|---|---|
| 一次只有一个请求（CP） | 等 B 算完 | 纯粹浪费 |
| 同时有 N 个请求（DP） | 各算不同请求 | **不存在冗余** |

所以问法应修正为「什么时候值得付这笔冗余」。

### 10.2 文献的做法

- **Megatron SP**（MLSys'23, arXiv:2205.05198）：把 TP 之后仍被复制的
  LayerNorm/Dropout 沿序列维切开，消除的是**显存**冗余；计算冗余本来就小。
- **Alpa**（OSDI'22）：逐算子选择复制或切分，明确「廉价算子允许复制」。
- **Shift Parallelism**（arXiv:2509.16495）：按流量在 TP 与 SP 之间动态切换，
  收益 1.51× 响应 / 50% 吞吐。
- **Amdahl 定量框架**（arXiv:2606.01927）：`A = 1/((1−P) + P/t)`，
  加速比被 `(1−P)` 卡死。

### 10.3 GR 上这个冗余几乎不存在

除注意力外，查表、投影、FFN 全都**按 token 可切**。真正不可切的只有
**固定开销 `b`** —— 而 `b` 就是 `S18` 测到的那个量（L=256 时占 92%）。

MTGR，L=8192，8 卡，`ρ=0.83`：

| 假设 | P | 延迟增益 | 吞吐代价 | 判断 |
|---|---|---|---|---|
| 只有 attn 可并行 | 48.7% | 1.67× | **4.80×** | 亏 |
| 所有 token 段可并行 | 100% | **5.61×** | 1.43× | 赚 |

| 模型（只有 attn 可并行） | P | 延迟增益 | 结论 |
|---|---|---|---|
| MTGR | 48.7% | 1.67× | 看是否要延迟 |
| LONGER | 3.2% | 1.03× | **不切** |
| HyFormer | 0.0% | 1.00× | **不切** |

### 10.4 判据与策略

```
Amdahl 上界 = T_dp / 不可并行部分 = (a+b+c+d) / (b_fixed + 段间规约)
```

| 上界 | 做法 |
|---|---|
| < 1.3× | 不切（DP，无冗余无通信） |
| 1.3–2.0× | 仅当延迟超 SLO 时切 |
| > 2.0× | 切，并把其余可切段一起切 |

**这个量由预测器直接给出**，因此可以**按请求**决定切不切——L=256 不切、
L=16384 切。这是 GR 相对 LLM 的独有能力（LLM 的 decode 时长均匀，只能按模型定）。

模块：`hetero/amdahl.py`（`stages_of` / `compare` / `breakeven_cards` / `serves_latency`）。

## 十一、GR 现有切分方式（文献）

详见 `GR切分方式-现状与文献.md`。总览是**三轨结构**，三轨动机完全不同：

| 轨 | 切什么 | 动机 | 代表 |
|---|---|---|---|
| ① 稀疏侧 | 嵌入表分片（TW/RW/CW/TWRW/GS） | **容量**（TB 级表） | TorchRec、HPS、OPER、Prism |
| ② 稠密侧 | 按 batch 复制（DP） | **吞吐**（稠密层小） | MTGenRec |
| ③ 长序列 | 按序列长度切（CP） | **显存**（激活随 L 涨） | RecSys'25 HSTU-Jagged-CP |

NVIDIA 的 HSTU 训练示例同时打开 ①②③：TorchRec 管表、Megatron-Core 管稠密侧
（DP/TP/SP/PP/CP）。

### 三个可直接引用的硬数字

**（1）单独开 CP 会降 scaling factor**（RecSys'25 Table 2，理想 2.00×）：

| 配置 | Scaling factor |
|---|---|
| 只 DDP | 1.6–1.7× |
| DDP + CP（cp_size=2） | **1.33×** |
| DDP + CP + batch 翻倍 | **1.55×** |

→ **CP 的产出是显存（序列 3K→16,384，5.3×），不是吞吐。**
切分本身不产生收益，要靠省下的显存换更大 batch 才兑现 1.55×。

**（2）TP 受注意力头数限制**（NVIDIA #71）：

> The TP size is limited by the attention heads.

已编码为 `max_tp_degree(shape)`：`heads=4` ⇒ TP ≤ 4。
GR 的头数通常比 LLM 少，这条会直接卡住方案。

**（3）按容量分片会让某分片成为关键路径**（arXiv:2011.02084）：
应按 pooling factor（每表期望查表次数）分片，而非按表大小。

### 两处文献空白

- **按组切 / 按组内 token 切**（`shard_r` / `shard_t`）：LONGER 类分组注意力的
  特有切法，文献无专门讨论。
- **段级切分**（同一次前向内每段不同卡数）：无任何 GR 文献涉及。
